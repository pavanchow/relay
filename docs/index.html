Relay is a from-scratch CI/CD engine whose scheduler is a pure, deterministic DAG executor you can unit-test without running anything. Give it a pipeline and it decides what runs, in what order, what runs in parallel, what gets skipped when a job fails, and what is served straight from a content-hash cache. Pick a preset below and press Run to watch the same rules resolve a job graph, live.

How to use this playground

Pick a preset to load a job graph: a diamond DAG, a failure that skips a subtree, a wide fan-out, or a cache hit. The jobs slider sets the concurrency limit (how many jobs may run at once), and fail-fast stops scheduling new work after the first failure.

Press Run and watch each node move through pending, running, and then success, failed, skipped, or cached, exactly as the scheduler resolves the graph. The event log and summary show the order and the peak concurrency actually observed against the limit. Reset clears the run.

It schedules by rule, not by luck

The core is one function, schedule::run(&pipeline, &mut executor, limits) -> Report. The scheduler never spawns a process or a thread. It drives an Executor trait in virtual time, so a MockExecutor that records what ran concurrently lets every rule be asserted deterministically. Swap in the ShellExecutor and the same scheduler runs real commands.

$ relay run examples/failure.relay
  [ 0] setup                ok       success
  [ 1] unit                 xx       failed
  [ 2] docs                 ok       success
       package              --       skipped
       deploy               --       skipped
summary: 2 success, 0 cached, 1 failed, 2 skipped

A failed job marks its transitive dependents skipped and they never run, while independent branches keep going. Parallelism is real and bounded: the mock proves the peak concurrency is exactly the limit and never more. Cache keys are a hand-rolled FNV-1a digest of a job's config plus its declared inputs, folded together with every upstream key, so a change in a non-cached upstream busts the downstream key too. Same pipeline, same result and same order, every run, with ties broken by config order.

Use it

# the whole test suite runs with no real processes, over the mock executor
cargo test
cargo clippy --all-targets -- -D warnings

# plan the DAG and wave order, run nothing
relay plan  examples/diamond.relay --jobs 2

# run a pipeline: print each status and a summary
relay run   examples/failure.relay

# print just the dependency graph
relay graph examples/diamond.relay
